The two rules

A binary heap is an array that encodes a binary tree obeying two invariants:

  1. Shape: the tree is complete — every level full, except possibly the last, which fills left to right. No holes.
  2. Order (heap property): in a min-heap, every parent ≤ its children. In a max-heap, every parent ≥ its children. Siblings have no order between them.

Consequence: the root (index 0) is always the minimum (min-heap) or maximum (max-heap). Nothing else is sorted.

Why O(log n)? A complete binary tree with n nodes has height ⌊log₂ n⌋ — a sift walks at most one root-to-leaf path.

The two sift walks

Two classic bugs (1) Sifting down and swapping with the larger child — breaks the property on the other branch. (2) Reading data[2*i+2] without checking right < n — one node in the tree can have a lone left child.

Pop, traced on [1, 3, 9, 7, 5]

save 1 (the answer)
move last (5) to root, shrink  → [5, 3, 9, 7]
sift down: children 3 and 9 → smaller is 3; 5 > 3 → swap
                               → [3, 5, 9, 7]
5 now at index 1: only child is 7; 5 < 7 → stop
returns 1, heap = [3, 5, 9, 7]

Why heapify is O(n)

Sift down every non-leaf, backwards from index n//2 - 1 to 0 (backwards so both subtrees are already valid heaps). Cost is bounded by each node's height, and the tree is bottom-heavy: ~n/2 leaves cost 0, ~n/4 cost 1, ~n/8 cost 2. The sum n · Σ(h/2^h) converges → O(n). A loop of n pushes would be O(n log n).

heapq quick API

Python's heapq operates on a plain list and is min-heap only.

import heapq

h = []                      # a heap is just a list
heapq.heappush(h, item)     # O(log n)
smallest = heapq.heappop(h) # O(log n)
smallest = h[0]             # peek, O(1)

nums = [7, 3, 9, 1, 5]
heapq.heapify(nums)         # in-place, O(n)

heapq.heappushpop(h, item)  # push then pop — faster than the pair
heapq.heapreplace(h, item)  # pop then push — heap size unchanged

heapq.nlargest(k, iterable, key=fn)   # top-k, O(n log k)
heapq.nsmallest(k, iterable, key=fn)  # bottom-k, O(n log k)

Three gotchas

  • heapify is in place and returns None. h = heapq.heapify(nums) gives you None.
  • heappop/heapreplace on an empty list raise IndexError. Guard with if h:.
  • h[0] is the minimum; h[-1] is not the maximum. Finding the max is O(n).

Max-heap in Python

No max-heap flag before 3.14. Negate on the way in and on the way out:

heapq.heappush(h, -x)
largest = -heapq.heappop(h)

Works only on numbers (-"abc" is a TypeError). For objects, push (-priority, item). Python 3.14 added heapify_max / heappush_max / heappop_max / heappushpop_max / heapreplace_max — do not rely on them in interviews.

Priorities on arbitrary payloads

Tuples compare lexicographically — element 0 first, element 1 only on a tie. So (priority, payload) is a priority queue for free… until two priorities tie and Python tries to compare the payloads:

TypeError: '<' not supported between instances of 'Task' and 'Task'

Data-dependent bug: passes every test with distinct priorities, explodes on the first collision. Fix with a strictly increasing tie-breaker in the middle, so comparison never reaches element 2:

counter = itertools.count()
heapq.heappush(h, (priority, next(counter), task))   # or enumerate's index

Bonus: equal priorities now pop in insertion order (FIFO). Source: Priority Queue Implementation Notes.

Top-K: two decisions before you type

A heap is a selector, not a sorter. Every top-k problem is the key (what you compare by) and the direction (which end you throw away).

The direction: opposite to the selection

The only cheap element is the root, and the root must be the next thing you evict — never the thing you want to return.

You wantBounded heap of size kRoot holdsAdmit newcomer when
k largestmin-heapsmallest of the keptnew > root
k smallestmax-heap (negate)largest of the keptnew < root

Unguarded heapreplace breaks a bounded heap: it pops before pushing, so a newcomer worse than everything held still displaces a member of the top-k. Size stays k; contents go wrong. Guard the call, or use heappushpop (pushes first, hands the newcomer back when it does not qualify).

There is no key= on heappush — only nlargest/nsmallest take one. Own the heap, own the decoration.

from typing import Any

class PrioritizedItem:

    item: Any = field(compare=False)   # excluded from __lt__

Monotone replacement

If f is strictly increasing over the data you have, ordering by f(key) equals ordering by key — so swap in any cheaper equivalent (drop a constant divisor, skip a root, stay in ints). Two traps:

  • Monotone only on part of the domain: sorted([-5,-1,0,2,3], key=lambda x: x*x) → [0,-1,2,3,-5]. Squaring is monotone for x ≥ 0 only.
  • Lossy "monotone" transforms merge distinct items. 10**17/(3*10**17) == (10**17+1)/(3*10**17) is True in floats; Fraction separates them correctly. Use Fraction (exact) or cross-multiplication (fast) for ratios.

nlargest / nsmallest: the contract

Signature is heapq.nlargest(n, iterable, key=None) — n is positional, there is no k=. They take any iterable (list, tuple, generator, dict.items()), never mutate it, and return a new list already ordered — descending for nlargest, ascending for nsmallest.

They do not operate on a heap: they build a private one of exactly n entries and heapreplace through the rest of the iterable. That is the bounded size-k heap, in stdlib form. Three cost paths, not one:

CaseWhat runsCost
n == 1max() / min(), no heapO(n)
n >= len(iterable)sorted(...)[:n]O(n log n)
otherwisebounded pass, then sort the k survivorsO(n log k) + O(k log k)

The final sort of the survivors is why the result comes back ordered — a heap alone would not give you that. The function is Python-specific; the algorithm is not (C++: std::partial_sort / std::nth_element; Java and JS: write it yourself). Say "size-k heap" outside Python.

Tie order

Docs define nlargest as equivalent to sorted(iterable, key=key, reverse=True)[:n] — and sorted is stable, so equal keys keep input order. Verified on 3.14 over 2000 collision-heavy inputs: element-for-element match. Your own heaps have no such promise — ties are undefined unless you put a counter in slot two.

The sign of that counter is not taste — it follows from the direction of the heap. CPython decorates as (key, counter, item) and signs it so the later arrival lands on the side that gets thrown away:

Private heapRoot it evictsCounter sequence
nlargestmin-heap of ksmallest kept0, -1, -2, …
nsmallestmax-heap of klargest kept0, 1, 2, …

Opposite signs, identical policy: earliest arrival survives. Derive the sign by asking which extreme does my heap discard, then make the newcomer that extreme. Only the relative order matters — the starting value is irrelevant and -0 == 0 is not an edge case. nlargest also guards with a strict if top < k, so an equal key never enters the heap at all: two independent mechanisms, same outcome.

Compare the key, not the tuple You push (ms, endpoint) to order by ms, then write if new > h[0] — and on a tie Python settles it by endpoint name, a decision you never asked for. Guards should read the key alone: if new_ms > h[0][0].

Three strategies, costed per phase

Never one aggregate number — cost each phase separately, then see which one survives. At n = 1e6, k = 10:

StrategyPhase 1Phase 2TotalExtra memory
sort allsort n by key — O(n log n)slice last k — O(k)O(n log n)O(n)
heapify allnegate + heapify — O(n)k pops, heap still size n — O(k log n)O(n)O(n)
bounded heapn arrivals, heap capped at k — O(n log k)drain the k survivors — O(k log k)O(n log k)O(k)

Phase 1 dominates in all three — at k = 10, phase 2 is noise. The counter-intuitive winner on time is heapify-all: O(n) beats O(n log k), so the folk answer "the bounded heap is the fast one" is wrong on that axis. The bounded heap wins on memory (O(k) vs O(n)) and is the only one that survives a stream. Winning on the wrong axis is not winning.

When the heap is the wrong tool

  • Large k → plain sorted(). k == 1 → min()/max(). Repeated calls → keep a real heap. (Straight from the docs.)
  • Streaming → the bounded heap is not just cheaper, it is the only option: heapify needs the whole collection at once.
  • Quickselect → O(n) average for the k-th element, O(n²) worst case. Know the name; out of scope here.
