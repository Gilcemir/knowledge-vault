Sift Down & Build Your Own Heap

Lesson 2 · ~30 min (lesson 10 min + drill 20 min) · ← Lesson 1 · cheat sheet

By the end of this lesson you will have written a working MinHeap from scratch — push, pop, peek, heapify — and know why heapify costs O(n) rather than O(n log n).

You already own half of this You traced 4, 8, 2, 6, 1 → [1, 2, 4, 8, 6] cold, on paper. That is sift-up, and it needs no more teaching. This lesson is about its mirror image — sift-down — and then about turning both into code.

1. The symmetry

Every heap operation is one of two walks along a single root-to-leaf path:

Sift upSift down
Used bypushpop, heapify
Starts atthe last indexindex 0 (or any node)
Compares againstthe parent (1 comparison)the smaller of two children (2 comparisons)
Stops whenparent ≤ item, or index 0 reacheditem ≤ both children, or a leaf reached

Sift-down is the harder of the two, for exactly two reasons — and both are where implementations break.

Trap 1: you must pick the smaller child

Going up there is only one parent, so there is no choice to make. Going down there are two candidates, and you must swap with the smaller one. Swap with the larger and you have just made a big value the parent of a small one — the heap property is broken and the bug surfaces many operations later, far from its cause.

Trap 2: a node may have only a left child

Because the last level fills left-to-right, exactly one node in the whole tree can have a lone left child. Code that blindly reads data[2*i + 2] raises IndexError — or worse, in a language without bounds checking, reads garbage. Always check right < len(data) before comparing children.

While sifting down, you must always swap the node with…

Swapping with the larger child would place a bigger value above a smaller sibling, breaking the parent ≤ child rule on the other branch. The smaller child is the only safe promotion.

In a heap of size n, nodes with no children start at index…

Index n//2 is the first leaf: its left child would be 2*(n//2)+1 ≥ n, which does not exist. So the entire second half of the array is leaves — a fact the next section exploits.

2. Why heapify is O(n), not O(n log n)

You could build a heap from n items with n pushes: O(n log n). But there is a better way, and it hinges on the fact you just answered: half the array is already leaves, and a single node is trivially a valid heap.

So: take the raw array as-is, and sift down every non-leaf node, walking backwards from index n//2 - 1 to 0. Going backwards matters — when you fix node i, both of its subtrees are already valid heaps, which is exactly the precondition sift-down needs.

Now count the work. Sift-down's cost is bounded by the node's height, not the tree's. And the tree is bottom-heavy:

LevelNode countMax sift-down cost each
leaves (bottom)~n/20
one above~n/41
two above~n/82
root1log n

The expensive nodes are rare and the cheap nodes are everywhere. Summing height × count over all levels gives n · Σ(h / 2^h), and that series converges to 2 — so the total is O(n) (MIT 6.006, Lecture 8; formal proof in CLRS §6.3).

Why this matters for interviews This is the difference between an O(n + k log n) answer and an O(n log n) one on top-k problems. Saying "heapify is linear, so I pay O(n) once instead of O(n log n)" out loud is a strong signal. You will use this in Lesson 4.

Building a heap from a list of n items costs, at best…

Bottom-up heapify is linear because most nodes sit near the bottom and barely move. A loop of n pushes would be O(n log n) — same result, worse cost.

3. The drill — write the heap

Knowledge is done; now the skill. Open the drill file and fill in the four TODOs:

python3 lessons/0002-minheap-drill.py

It ships with a test harness that gives you immediate feedback, including a 300-trial randomized stress test against Python's own heapq. Right now everything reports not implemented. Your job is six green lines.

Try it — 20 minutes
  1. Open 0002-minheap-drill.py and implement peek, push, pop, and heapify.
  2. Do not import heapq in your implementation — the harness imports it only to check you.
  3. Factor out a private _sift_down(i) helper. Both pop and heapify need it; writing it twice is how the two traps above sneak in twice.
  4. Run the file after each method. Watch .. turn into ok.
  5. When all six pass, read CPython's heapq.py and find one thing it does differently from yours.

Stuck? Ask your teacher for a hint. You will get the smallest hint that unblocks you — never the answer.

Gotcha — your array may differ from heapq's, and that's fine If you compare your internal array against heapq's after a pop, they will sometimes disagree. This is not a bug. CPython's _siftup walks all the way down the minimum-child path and then bubbles the item back up — a different route to a valid heap. Verified empirically over 20,000 random pops: the popped value always matches, both arrays are always valid heaps, and they hold the same elements — but the arrangement differs in roughly 10% of cases. This is why the harness checks the heap property and the popped sequence, never array equality. Any array satisfying the two rules is a legitimate heap.

4. Retrieval check (no peeking at Lesson 1)

You pop from [2, 5, 3, 9, 6]. Which value moves to index 0 first?

Pop always starts by moving the last element to the root — that is the only removal that keeps the tree complete. Then it sifts down, and only then does the smaller child (3) come into play.
