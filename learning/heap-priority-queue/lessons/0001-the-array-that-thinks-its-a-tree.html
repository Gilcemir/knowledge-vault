The Array That Thinks It's a Tree

Lesson 1 · ~25 min · Heap/Priority Queue track · cheat sheet

By the end of this lesson you will be able to look at a plain Python list like [1, 3, 9, 7, 5] and see the tree hiding inside it — and explain why heapq never needs node objects or pointers.

1. Priority queue ≠ heap

Two words that get used interchangeably, but shouldn't be:

  • A priority queue is an abstract data type: a bag of items where you can only ask for "the most important one next". It's a contract — push, pop-best, peek-best.
  • A binary heap is a concrete data structure — the most popular way to implement that contract efficiently.

You could implement a priority queue with a sorted list (pop is O(1), but push is O(n)) or an unsorted list (push is O(1), but pop is O(n)). The heap is the famous compromise: both in O(log n) (MIT 6.006, Lecture 8).

A "priority queue" is best described as…

Priority queue is the contract (push / pop-best / peek-best). The binary heap is one implementation of it — the one Python's heapq uses.

2. The two rules of a heap

A binary min-heap is a binary tree obeying exactly two invariants:

  1. Shape rule — the tree is complete: every level is full except possibly the last, which fills strictly left-to-right. No gaps, ever.
  2. Order rule (the heap property) — every parent ≤ its children. That's it. Siblings are not ordered relative to each other.

Check both rules against the picture: every level full except the last (which leans left) ✓, and every parent ≤ its children (1≤3, 1≤9, 3≤7, 3≤5) ✓. Notice 9 sits above 7 and 5 in the array order — that's fine. A heap is not sorted. The only global guarantee is: the root is the minimum.

Which statement is guaranteed by a min-heap?

Only the parent↔child relation is constrained. The array as a whole is not sorted, and siblings (left vs right child) have no order between them.

3. The array trick

Here's the beautiful part. Because the shape rule forbids gaps, you can lay the tree out level by level in a flat array — and recover every parent/child relationship with arithmetic alone:

RelationFormula (0-based)
Parent of i(i - 1) // 2
Left child of i2*i + 1
Right child of i2*i + 2

No node objects, no pointers, no .left/.right — just index math on a list. This is why heapq operates directly on plain Python lists (Python docs — heapq), and why heaps are so memory-cheap and cache-friendly.

In a 0-based heap array, the parent of index 4 is at index…

(4 - 1) // 2 = 1. Check it on the picture above: node 5 (index 4) hangs off node 3 (index 1).

The left child of index 3 lives at index…

2*3 + 1 = 7. In our 5-element array index 7 doesn't exist — which is precisely how code detects that index 3 is a leaf.

4. Why O(log n)? (the 10-second argument)

A complete binary tree with n nodes has height ⌊log₂ n⌋ — doubling the data adds just one level. Every heap operation you'll meet (push, pop) walks at most one root-to-leaf path, fixing the order rule as it goes. Path length = tree height = O(log n). Peeking the minimum is just reading h[0]: O(1). The how of that walking (sift-up / sift-down) is the whole subject of Lesson 2, where you'll implement it yourself.

You push [7, 3, 9, 1, 5] one by one with heappush. The final list is…

Not sorted — just heap-valid! Each push appends then bubbles up only along its parent path. Verify every parent ≤ children: 1≤3, 1≤9, 3≤7, 3≤5. The middle option is what a sorted list would look like — heaps don't promise that.

Try it — 10 minutes, paper first
  1. On paper, insert 4, 8, 2, 6, 1 one at a time into an empty min-heap, drawing the tree after each insert (new item goes in the next free slot, then swap upward while smaller than its parent).
  2. Write your final answer as an array.
  3. Now check yourself in the Python REPL: 
    import heapq
h = []
for x in [4, 8, 2, 6, 1]:
    heapq.heappush(h, x)
    print(h)   # watch the array after every push
  4. If any intermediate state surprises you, replay it on VisuAlgo's heap visualizer — watch the swap path light up.
