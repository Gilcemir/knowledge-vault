heapq Fluency

Lesson 3 · ~30 min (lesson 12 min + drill 18 min) · ← Lesson 2 · cheat sheet

By the end of this lesson you will drive Python's heapq without thinking about it: max-heaps out of a min-only library, priorities attached to arbitrary payloads, and the two combined operations most people never learn.

You just built one of these Your MinHeap passes all six tests, stress test included. From here on you never write that code again — in an interview you say "I'll use a heap" and reach for heapq. This lesson is about the gap between knowing how a heap works and typing the right four lines under pressure.

1. The mental model: there is no heap object

heapq is not a class. It is a set of functions that operate on a plain list you already own, maintaining the invariant you implemented by hand:

import heapq

h: list[int] = []           # this is the heap. it is a list.
heapq.heappush(h, 5)
heapq.heappush(h, 1)
smallest = h[0]             # peek — O(1), just indexing
smallest = heapq.heappop(h) # O(log n)

Two consequences fall straight out of that:

  • len(h), if h:, iteration, slicing — all the list things still work. if h: is your emptiness check; heappop on an empty list raises IndexError.
  • Nothing stops you from mutating h directly and destroying the invariant. The library trusts you.
Gotcha — heapify returns None heapq.heapify(nums) rearranges nums in place and returns None. Writing h = heapq.heapify(nums) silently hands you None, and the failure surfaces three lines later as TypeError: object of type 'NoneType' has no len(). Same shape of bug as nums = nums.sort().

heapq.heapify(nums) gives you back…

In-place, linear time, returns None — exactly like list.sort(). Bind the list first, heapify it second: h = list(nums); heapq.heapify(h).

2. The library is min-only. Negate.

There is no max=True flag. The standard move is to store negated values and negate again on the way out:

h: list[int] = []
for x in nums:
    heapq.heappush(h, -x)   # in goes -x
largest = -heapq.heappop(h) # out comes x

It works because negation reverses the order of numbers: if a > b then -a < -b, so the "smallest negative" is the largest original. Two limits worth knowing:

  • It only works on things you can negate — numbers. Strings, tuples of strings, objects: no. For those, wrap them in a tuple with a numeric priority (next section), or push (-priority, payload).
  • Forgetting one of the two negations is the single most common heap bug in Python. Negate on the way in and on the way out.
Python 3.14 added real max-heap functions — ignore them for now heapify_max, heappush_max, heappop_max and friends landed in Python 3.14. Your machine runs 3.9, and interview judges lag years behind. Learn the negation trick as the real answer; mention 3.14 only as a footnote if someone asks.

The negation trick fails outright when items are…

-"abc" is a TypeError. Floats negate fine and lose nothing; tuples of numbers can be negated element-wise, and left-to-right comparison is a feature you are about to exploit.

3. Tuples: attaching a priority to anything

Python compares tuples lexicographically — first elements first, and only on a tie does it look at the second. That is exactly a priority queue:

heapq.heappush(h, (priority, payload))
priority, payload = heapq.heappop(h)   # lowest priority number wins

And here is the trap that the official docs devote a whole section to:

Tuple comparison breaks for (priority, task) pairs if the priorities are equal and the tasks do not have a default comparison order.

When two priorities tie, Python moves on to element two and tries task_a < task_b. If your payload is a custom object with no __lt__, you get:

TypeError: '<' not supported between instances of 'Task' and 'Task'

What makes this vicious is that it is data-dependent. Your code runs fine on every test case with distinct priorities and explodes the first time two collide.

The fix: a monotonic tie-breaker in the middle

Insert a strictly increasing counter as element two. No two entries ever share one, so comparison stops there and never touches the payload:

import itertools

counter = itertools.count()
heapq.heappush(h, (priority, next(counter), task))

You get two things for the price of one: the crash is impossible, and equal-priority items now come out in insertion order — a FIFO tie-break, which is usually what you wanted anyway. In a loop you already have an index, so enumerate does the same job without importing anything.

Pushing (2, task_a) then (2, task_b) raises TypeError because…

Equal first elements send tuple comparison to element two — the payloads. Duplicate priorities are perfectly legal; three-element entries are the fix, not the requirement.

4. Two combined operations worth memorising

Both do a push and a pop in one pass instead of two, and they are not the same function:

heappushpop(h, x)heapreplace(h, x)
Orderpush x, then poppop, then push x
Returnsthe smaller of x and h[0]the old h[0] — possibly larger than x
If x is the new minimumhands x straight back, heap untouchedstill evicts the old root
Empty heapfine — returns xIndexError

Concretely, on h = [2, 7, 5] with x = 1: heappushpop returns 1 and leaves the heap alone, while heapreplace returns 2 and the heap becomes [1, 7, 5]. Same inputs, different answers. The docs put it plainly: "The value returned may be larger than the item added. If that isn't desired, consider using heappushpop() instead."

5. nlargest and nsmallest

heapq.nlargest(3, nums)                      # → list, descending
heapq.nsmallest(3, people, key=lambda p: p.age)

Read the contract carefully, because nothing here is a heap operation: the count is positional (no k= keyword), the second argument is any iterable (not a heap, and it is not turned into one), nothing is mutated, and what comes back is a new list, already ordered — descending for nlargest, ascending for nsmallest. Under the hood each one keeps a private heap of exactly k entries; Lesson 4 unpacks that.

The n that is not your n The docs write this parameter as n: nlargest(n, iterable). In cost analysis n means input size. These materials always call the count k, because crossing the two flips O(n log k) into the wrong O(k log n). The pass is over the whole input; the log is of the little heap.

They take a key=, like sorted(), and they run in O(n log k) — cheaper than sorting when k is small. The docs are refreshingly honest about the boundaries: for large k, plain sorted() is faster; for k == 1, use min()/max(); and if you are calling them repeatedly, build a real heap instead.

Interview caution nlargest is a one-liner for problems whose whole point is the heap. Reaching for it can read as dodging the question. Know it, use it in real code, but in an interview say what it costs and offer to write the loop underneath.

7. Retrieval check

heapreplace(h, x) can return a value…

It pops before pushing, so it always evicts the old root even when x is smaller. heappushpop is the one that returns the smaller of the two.

In a min-heap array, the final element is…

The heap property constrains parents against children, nothing else. The maximum is guaranteed to be some leaf, but not the last slot. Finding it is O(n) — heaps are one-ended.
