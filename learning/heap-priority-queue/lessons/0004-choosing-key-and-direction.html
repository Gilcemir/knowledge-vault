Choosing the Key, Choosing the Direction

Lesson 4 · ~30 min (lesson 12 min + drill 18 min) · ← Lesson 3 · cheat sheet

A heap is a selector, not a sorter. You already own the machine — you built one in Lesson 2 and drove the library one in Lesson 3 — and you have pointed it at two problems. What is left is the part that happens before you type: every top-k problem collapses into two decisions.

  1. The key — what are you comparing by?
  2. The direction — which end are you throwing away?

Get those two right and the code is four lines you already know. Get either wrong and no amount of heapq fluency saves you.

What this lesson does not do It does not re-teach the bounded size-k heap. You derived that yourself on LC 703 without a hint. This lesson is about the two choices you made implicitly there, so that next time you make them on purpose — plus the cost accounting that made P2's complexity answer right for the wrong reason.

1. The key is a function, not a field

A priority is rarely sitting in the data waiting to be read. Usually it is computed from the payload. Python gives you three places to put that computation:

WhereLooks likeUse when
key=nlargest(k, items, key=f)One-shot selection over a finished collection
Decorated tuple(f(x), tiebreak, x)A heap you push to and pop from over time
Wrapper class@dataclass(order=True)The payload is an object you push repeatedly

key= exists only on nlargest/nsmallest (and sorted, min, max). There is no key= on heappush. The moment you own the heap, you own the decoration — that is why the tuple pattern from Lesson 3 keeps coming back.

The third option comes straight out of the docs, and it is worth knowing because it makes the payload uncomparable by construction:

from dataclasses import dataclass, field
from typing import Any

@dataclass(order=True)
class PrioritizedItem:
    priority: int
    item: Any = field(compare=False)

field(compare=False) excludes item from the generated __lt__, so two equal priorities compare equal instead of exploding. Same problem the counter solved in Lesson 3, different tool.

Gotcha — the heap compares what you pushed, not what you meant You push (ms, endpoint) because you want to order by ms. Then you write a guard like if new_entry > h[0], and on a tie Python quietly moves to element two and settles it by endpoint name — a decision you never asked for. If your comparison is supposed to be about the key alone, compare the key alone: if new_ms > h[0][0]. The tuple is for the heap's internal ordering; your guards are yours.

Monotone replacement: the same order, cheaper

If f is strictly increasing over the values you actually have, then ordering by f(key) and ordering by key give the same result. So you may freely swap in any cheaper f-equivalent: drop a constant divisor, skip a root, keep integers instead of floats. The comparisons cannot tell the difference.

That cuts the other way too — a "harmless" transform that loses information silently merges items that were never equal. Ranking by wins / games, verified on Python 3.14:

a = (10**17, 3 * 10**17)        # exactly 1/3
b = (10**17 + 1, 3 * 10**17)    # strictly larger than 1/3

a[0] / a[1] == b[0] / b[1]              # True   ← float division collided
Fraction(*a) == Fraction(*b)            # False
Fraction(*a) <  Fraction(*b)            # True   ← exact, and still just a key

Both are monotone in intent; only one is monotone in fact. Fraction is the exact key when a ratio matters, and cross-multiplication is the fast one.

Monotone only on your domain Squaring is strictly increasing for non-negative values — and folds the number line in half otherwise. Sorting [-5, -1, 0, 2, 3] by x*x gives [0, -1, 2, 3, -5]. Before you replace a key, ask what range the data actually spans.

Ordering by f(key) matches ordering by key whenever f is…

Only monotonicity preserves order. Cheapness is why you bother, not whether it is valid — and a transform applied after popping cannot influence an order that was already decided.

2. The direction — derive it, don't memorise it

Here is the whole argument, and it is three sentences long. You are allowed to hold only k items. A new one arrives, and if it deserves a slot then one resident has to die. Which resident?

Keeping only the k largest, the element you must see instantly is the…

The victim is always the weakest survivor, so that is the one you compare the newcomer against — and a heap gives you exactly one element for free: the root. Therefore the root must hold the smallest of the k largest.

That answer is the rule. The heap runs opposite to the selection, because the only cheap element is the root and the root has to be the next thing you throw away:

You wantBounded heap of size kRoot holdsAdmit the newcomer when
k largestmin-heapsmallest of the keptnew > root
k smallestmax-heap (negate)largest of the keptnew < root

The direction feels backwards the first few times. The check that unsticks it: name the element you want to be able to evict in O(1) — never the one you want to return.

Which is why heapreplace is the wrong verb here

Lesson 3 gave you the mechanics of heappushpop versus heapreplace. Now they have consequences.

Unconditional heapreplace on a full size-k heap can…

heapreplace pops before it pushes, so it removes the root unconditionally — even when the newcomer is worse than everything you are holding. The size stays exactly k (that part is fine) and it never raises on a non-empty heap. What breaks is the contents: a value that does not belong in the top-k has displaced one that did.

So a bounded heap needs a decision before the mutation: either guard the call (if new > h[0]), or use heappushpop, which pushes first and therefore hands the newcomer straight back when it does not qualify. Both work. They are not interchangeable on ties — see the gotcha in section 1, and Part B of the drill will hold you to it.

3. Cost, one phase at a time

Why this section exists On P2 you answered O(n log n) — correct — and attributed the log factor to heapify, which has none. The total was right while the model underneath was wrong, and that is invisible from the total alone. The fix is mechanical, and it is the habit this lesson is really selling: write each phase separately, add them, then drop the smaller term. Never reason from one aggregate number.

"Give me the k slowest of n requests" has at least three honest answers. Each is two phases:

StrategyPhase 1Phase 2
sort_allsort all n by the keytake the last k
heapify_allnegate all n, heapifypop k times
boundedone pass, heap capped at kdrain the k survivors

Costing these is Part A of the drill, so the numbers are not here. What is here is the warning: one of the three beats the bounded heap on time for small k, and it is not the one most people would name. Do the accounting phase by phase and it falls out in a minute. Reason from the aggregate and you will get the folk answer.

Two axes, not one, decide the winner in practice: time and peak memory. Keep them separate in your head.

4. When the heap is the wrong tool

The docs are unusually candid about their own functions:

The latter two functions perform best for smaller values of n. For larger values, it is more efficient to use the sorted() function. Also, when n==1, it is more efficient to use the built-in min() and max() functions. If repeated usage of these functions is required, consider turning the iterable into an actual heap.

Add two more boundaries the docs do not mention:

  • Streams. heapify needs the whole collection at once. If items arrive over time and you must answer at any moment, the bounded heap is not merely cheaper on memory — it is the only one of the three that is possible. That is the reconciliation for section 3's puzzle.
  • Quickselect finds the k-th element in O(n) average time, beating every heap strategy — with a worst case of O(n²) unless you fight for it. Out of scope for this track; know the name so an interviewer's "can you do better than the heap?" does not land cold.

5. nlargest / nsmallest, defined

Lesson 3 gave you the signature and the headline cost. The rest of this lesson leans on the full contract, so here it is:

QuestionAnswer
Signatureheapq.nlargest(n, iterable, key=None) -> list — n is positional; there is no k=
What it acceptsAny iterable — list, tuple, generator, dict.items(). Not a heap.
What it returnsA brand-new list, already ordered: descending for nlargest, ascending for nsmallest
What it mutatesNothing. The input comes out untouched.

They do not operate on a heap — they build one

This is the sentence to hold on to. Your input is not a heap and is never turned into one. Internally the function decorates each item, keeps a private heap of exactly n entries, and heapreplaces as it walks the rest of the iterable. That is the bounded heap of section 2, in production form — which is precisely why Part B bans it. Reaching for nlargest there would skip the exercise.

The cost has two shortcuts the headline hides

O(n log k) is only the general path. CPython checks two cheaper cases first:

CaseWhat it actually runsCost
n == 1max() / min() — no heap at allO(n)
n >= len(iterable)sorted(iterable, key=key, reverse=True)[:n]O(n log n)
otherwisebounded-heap pass, then a final sort of the k survivorsO(n log k) + O(k log k)

That final sort of the survivors is why the result comes back ordered — a heap alone would not give you that. And note the second row: the docs' own advice from section 4 is applied to you by the function itself.

Python-specific? The function is — heapq.nlargest is stdlib sugar. The algorithm is not: bounded-heap selection is universal. C++ ships std::partial_sort and std::nth_element; Java and JavaScript ship nothing equivalent and you write the bounded heap by hand. Cite nlargest in a Python interview; say "size-k heap" everywhere else.

6. What decides a tie in nlargest

The docs define these two by equivalence, which pins tie order exactly:

Equivalent to: sorted(iterable, key=key, reverse=True)[:n]

Python's sorted is stable, so equal keys keep their original relative order — and nlargest is built to reproduce that, not just the multiset. Verified here on 3.14 over 2000 random inputs with heavy key collisions: nlargest and nsmallest matched the sorted(...)[:n] slice element for element, every time. Part C makes you predict it before you run it.

It can promise that because the decoration from section 5 is not (key, item) but (key, arrival_counter, item). On a tie the comparison moves to slot two and is settled by arrival order — never reaching the payload, which is the gotcha from section 1 solved properly. Which way the counter has to run for the earlier arrival to win is the decision Part B hands you, so it is not written down here.

Do not carry that habit into your own heaps Stability is a promise of nlargest/nsmallest, not of heaps. A heap you build yourself has no tie order at all unless you put one there — that is the counter in slot two. The docs even say of their heapsort example: "unlike sorted(), this implementation is not stable."

8. Retrieval check

Ordering by x*x reverses pairs when the values are…

Squaring is monotone only on non-negatives. Below zero it reverses: −5 < −1, but 25 > 1. Fractions shrink under squaring yet keep their order; equal values stay equal, harmlessly.

A key= argument is accepted by heapq's…

Only the two selection helpers take a key. Everything that mutates a heap compares the items exactly as you pushed them — so on those, the key has to be baked into the pushed value.
