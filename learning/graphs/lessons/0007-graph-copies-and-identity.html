L3 — Copying a Graph: Identity and the old→new Map

Graphs track · lesson 3 of the main line · ~25 min · 2026-08-20 · prereq: L2 — DFS with Cycles

The problem first — hand over the network without handing over yours

Yesterday's P2 review ended on an open wound: your maxAreaOfIsland zeroed cells in place, and we saw that this destroys the caller's grid — whoever gave you that grid gets it back ruined. The production fix we named was: work on a copy. For a grid that's two lines:

grid_copy = [row[:] for row in grid]   # row[:] returns a NEW list holding the same elements

Now the same request lands on the friendship network from L1. A teammate's function runs a destructive analysis — it deletes edges as it works, exactly like your dfs zeroed cells. You must hand it the network without losing yours. So: copy the graph. How hard can it be?

Hard enough to be a roadmap problem. By the end of this lesson you'll know the one template that solves it — and that template is P3, Clone Graph (LC 133), waiting for you at the end.

What a variable actually holds

First, the mechanism behind the P2 wound. Why did the caller's grid change, when the caller never ran your code on their own variable? Because a Python variable does not hold a value — it holds an arrow. Three new nouns, all visible in one picture:

a = [1, 2]
b = a          # copies the ARROW, not the list
c = [1, 2]     # builds a SECOND list that happens to look the same
TermIn the picture
referencethe arrow. Every variable, list slot, and dict value is one. The list object lives elsewhere; the name just points at it.
aliasinga and b are two names, one object. Mutate through either name and the other "sees" it — there is no other, there's one list. This is exactly how your dfs reached the caller's grid.
identitywhich object an arrow lands on. is compares identity (same object?); == compares contents (same value?). ① and ② are equal but not identical.

After a = [1, 2], then b = a, then b.append(3) — what does a hold?

b = a copied the arrow. There is exactly one list object in that program, with two names on it. Appending through b and reading through a touch the same memory.

Shallow copy — one level deep is not deep

So copying means: build a new object. Python dicts ship a method for that — contract first: d.copy() takes no arguments, returns a new dict with the same keys and values, and leaves d untouched. Sounds like the fix. Try it on L1's adjacency dict:

adj = {0: [1], 1: [0]}
new = adj.copy()      # new dict — adj is not new is True
new[0].append(9)      # mutate through the copy...
print(adj[0])         # [1, 9]  ← ...and the ORIGINAL changed

The outer dict is new, but its values are references — the same arrows, landing on the same inner lists. The Python docs give this failure a name, defined precisely (docs.python.org — copy):

TermDocs definition (verbatim)
shallow copy"constructs a new compound object and then (to the extent possible) inserts references into it to the objects found in the original."
deep copy"constructs a new compound object and then, recursively, inserts copies into it of the objects found in the original."

Your grid fix [row[:] for row in grid] was a hand-rolled deep copy: new outer list, and a new inner list per row. It worked because a grid is exactly two levels deep and the innermost values ("0"/"1" strings) are immutable — nothing deeper to chase.

Given adj = {0: [1], 1: [0]} and new = adj.copy(), after new[0].append(9) — what is adj[0]?

Shallow means the copy stops at level one: new dict, same arrows inside it. new[0] and adj[0] are aliases of a single list — the picture from the previous section, wearing a dict.

A graph made of objects

One more twist before the real problem. So far every graph you've touched was an adjacency dict that you held whole in one variable. LC 133 hands you the graph in a different costume — each vertex is an object, and edges are references stored inside it:

class Node:
    def __init__(self, val: int = 0, neighbors: list["Node"] | None = None) -> None:
        self.val = val
        self.neighbors: list[Node] = neighbors if neighbors is not None else []

Build the triangle from L2 in this costume:

n1, n2, n3 = Node(1), Node(2), Node(3)
n1.neighbors = [n2, n3]
n2.neighbors = [n1, n3]
n3.neighbors = [n1, n2]

Map the new representation onto the one you already own — same graph, different clothes:

Adjacency dict (L1)Node objects (this lesson)
a vertex is a key: 0, 1, 2a vertex is the object itself: n1
its label is the key valueits label lives in u.val
its neighbors: adj[u], a list of keysits neighbors: u.neighbors, a list of references
you hold the whole graph in one dictyou hold one node; edges lead to all the rest

That last row matters: LC 133 gives you a single reference to one node. Everything else is reachable only by walking edges — which is why cloning is a traversal problem, not a loop-over-keys problem.

Clone it — the L2 crash returns

You know a traversal. Port it naively: to clone a node, make a fresh Node with the same label, then clone each neighbor:

def clone(u: Node) -> Node:
    copy = Node(u.val)
    for v in u.neighbors:
        copy.neighbors.append(clone(v))
    return copy

Trace on the triangle, one row per call — you already know the shape of what's coming:

#callwhat it does
1clone(n1)builds a fresh clone of 1; first neighbor n2 → recurse
2clone(n2)builds a fresh clone of 2; first neighbor n1 → recurse
3clone(n1)builds a second clone of 1; first neighbor n2 → recurse
⋮⋮…≈1000 frames later: RecursionError

Same disease as L2's naive DFS — the cycle re-enters vertices forever. But look at row 3: this version was also mass-producing duplicate clones on the way down. Two failures, and they demand the same cure they demanded in L2: never re-enter a vertex.

Why a visited set is not enough

So reach for L2's cure — a visited set — and watch it come up short:

visited: set[Node] = set()

def clone(u: Node) -> Node:
    visited.add(u)
    copy = Node(u.val)
    for v in u.neighbors:
        if v not in visited:
            copy.neighbors.append(clone(v))
        else:
            copy.neighbors.append(???)   # v was cloned earlier... but WHERE is that clone?
    return copy

The recursion is tamed, but stand inside that else branch at n2, looking at already-visited n1. The copy of the triangle needs the edge 2–1 to exist, so something must be appended. The set can answer "have I seen n1?" — it cannot answer "and where did I put n1's clone?". You did the work; you just can't find it again.

In that else branch at n2, with n1 already visited — what does c2, the half-built clone of n2, need right now?

Skipping drops the edge 2–1 from the copy (in L2, skipping was fine — a traversal only had to reach things; a copy has to rebuild things). Appending the original leaks your graph into the "copy" — aliasing again. A second clone forks vertex 1 in two. Only the existing clone preserves the shape — and a set can't hand it back.

The fix — upgrade the set to a map: old → new

The visited set needs to remember one more thing: for each original, where its clone lives. A set that stores an answer is a dict. This is the whole lesson:

old_to_new: dict[Node, Node] = {}

def clone(u: Node) -> Node:
    if u in old_to_new:              # "visited" check — the keys ARE the visited set
        return old_to_new[u]         # ...and now it can HAND BACK the clone
    copy = Node(u.val)
    old_to_new[u] = copy             # register BEFORE wiring neighbors — L2's mark-on-entry
    for v in u.neighbors:
        copy.neighbors.append(clone(v))
    return copy

Two deliberate differences from L2's dfs template — map them before they bite you:

L2 dfs(u)clone(u)
guard livesat the call site: if v not in visited: dfs(v)inside, first line: if u in old_to_new: return …
returnsnothing — visiting was the pointthe clone — the caller needs it every time, seen or not, so the call can never be skipped
mark on entryvisited.add(u) before the loopold_to_new[u] = copy before the loop

(P2 already made you grow the "dfs returns something" muscle — this is that muscle again, returning an object instead of an area.)

Register before wiring — L2's rule in new clothes Move old_to_new[u] = copy to after the neighbor loop and the protection evaporates: cloning n1 recurses into n2, which looks up n1 — not registered yet, since n1's loop hasn't finished — and recurses straight back into it. Infinite ping-pong, with the map sitting right there. The moment the clone exists, it goes in the map — before any neighbor is wired.

One Python footnote so the dict doesn't feel like magic: Node objects work as dict keys because instances of user-defined classes are hashable by default — hashed by identity, each object equal only to itself. Which is precisely what you want: two nodes with the same val are still two different vertices.

Now the paper trace — full state table on the triangle, starting at clone(n1):

#callold_to_new after registeru.neighborsdecisions
1clone(n1){n1→c1}[n2, n3]clone(n2) → not in map → recurse (row 2)
2clone(n2){n1→c1, n2→c2}[n1, n3]clone(n1) → map hit, append c1; clone(n3) → recurse (row 3)
3clone(n3){n1→c1, n2→c2, n3→c3}[n1, n2]clone(n1) → map hit, append c1; clone(n2) → map hit, append c2; return c3
4—unchanged—row 2 appends c3, returns c2; row 1 appends c2, then clone(n3) → map hit, appends c3; done

Two triangles, zero shared vertices. And is — not == — is the tool that proves it:

copy1 = clone(n1)
assert copy1 is not n1                 # a new object, not an alias
assert copy1.val == n1.val             # same label
assert copy1.neighbors[0] is not n2    # edges lead to clones, never to originals

A "copy" that leaks one original into its neighbor lists passes every == test you can write and fails the third assert instantly. Identity checks are how graph copies are judged — LC 133's judge does exactly this.

clone(n1) on the triangle, template above: how many clone() calls happen in total, and how many of them build a new Node?

Count by structure, not by guess: one top-level call, plus one call per neighbor-list entry — the triangle's lists hold 2 + 2 + 2 = 6 entries — so 1 + 6 = 7. The map answers 4 of them instantly; exactly V = 3 reach the build line, one per vertex.

That count is the cost argument, done:

phasecost
Node creationsV — each original enters the map exactly once
clone() calls1 + one per neighbor entry = 1 + 2E (undirected: each edge listed twice)
timeO(V + E) — same bound as L2's traversal, for the same reason
spaceO(V) for the map and the clones, plus O(V) worst-case recursion stack

The stdlib already ships this

Contract first: copy.deepcopy(obj) takes any object, returns a new object rebuilt recursively, and leaves the original untouched. How does it survive an object that contains a cycle — like every undirected graph? The docs answer verbatim: it works by "keeping a memo dictionary of objects already copied during the current copying pass."

Read that again. The memo dictionary is old_to_new. You just re-derived the engine inside copy.deepcopy — the same way the heap track ended with you re-deriving heapq. In production, reach for deepcopy. On LC 133, the point is to build the engine yourself.
