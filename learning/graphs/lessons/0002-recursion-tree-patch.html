Draw the tree — all of it

The P1 code makes one binary decision per element: take it or skip it. Two calls, always — dfs(i+1) after the append and dfs(i+1) after the pop. For [1, 2]:

                     dfs(0)  path=[]
                   /                \
             take 1                  skip 1
                 /                     \
        dfs(1) path=[1]           dfs(1) path=[]
         /          \              /          \
    take 2        skip 2       take 2       skip 2
       /              \          /              \
 dfs(2)           dfs(2)     dfs(2)          dfs(2)
 [1,2]             [1]        [2]              []
  leaf #1         leaf #2    leaf #3         leaf #4

Every internal node has exactly two children. So the level widths are 1, 2, 4, 8, … — the leaf count is always a power of 2. A 3-leaf prediction isn't just wrong, it's structurally impossible for this code. That's the sanity check you now own: count the leaves before predicting the output.

The one fact this patch exists for Each of the n elements doubles the tree: leaves = 2n. Different leaves see different paths because the pop runs between the take-branch and the skip-branch — that's the same green fact you already had in K3, now applied to counting.

How many leaves does the subsets tree on 3 distinct items have?

Three binary decisions: 2 × 2 × 2 = 2³ = 8. Level widths go 1, 2, 4, 8 — never 6 or 9, those aren't powers of two.

Which subset does f([1, 2, 3]) append to res LAST?

The take-branch always recurses before the skip-branch, so all-take ([1,2,3]) is first and all-skip ([]) is last.

What the whole tree costs

K7 asked for total work, "including materializing each subset at the leaf". Two numbers, multiplied:

QuantityValueWhy
How many leaves2none binary decision per element
Work per leafup to npath.copy() copies up to n items
TotalO(n · 2n)leaves × per-leaf copy — the copies are not free

This multiplication — count the nodes, then multiply by the work at each node — is the exact cost argument Erickson makes for every backtracking algorithm, and it's the same one you'll use in two lessons for graphs: DFS cost = (vertices visited) × (work per vertex) + (edges scanned). Same muscle.

n = 10 gives 1,024 leaves, and each leaf copies up to 10 items. Roughly how many operations in total?

1,024 leaves × ~10 copied items each ≈ 10,240 — that's n · 2ⁿ. Answering 1,024 is counting leaves but pretending the copies are free.

Why this gates the Graphs track DFS on a graph is this same engine — the visited set you'll meet in L2 is K6's used flag with one brutal difference: it is never released. If you can't see the tree a DFS walks, you can't say what a graph traversal costs. That's why this patch came before L1.
