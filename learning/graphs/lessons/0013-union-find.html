L7 — Union-Find

Graphs track · lesson 7 of the main line · ~30 min · 2026-11-05 · prereq: L2 — DFS with Cycles (components), L4 — BFS: Layers Are Distances · drill: 0014-union-find-drill.py · reference: Union-find

The problem first — cables arriving one at a time

Six computers, numbered 0 to 5, and no cables yet. Events arrive one at a time, of two kinds:

  • connect a b: a cable is plugged in between a and b. Cables work both ways.
  • ask a b: can a reach b right now, through any chain of cables?

This stream:

connect 0 1     connect 2 3     ask 0 3     connect 1 3
ask 0 2         connect 4 5     ask 5 0
Answer every ask at the moment it arrives, before the next event is read.

Sedgewick & Wayne call this the dynamic connectivity problem: "The input is a sequence of pairs of integers, where each integer represents an object of some type" (Algorithms §1.5, verified 2026-11-05). Cables are only ever added, never removed.

Try your BFS first

You already own the tool for "can a reach b?": L4's BFS from a, stopping when b is popped. For each ask, run BFS on the cables plugged in so far. The answers come out right: no, yes, no.

Now count. One BFS may touch every vertex and every cable, which is O(V + E). The graph changes after every connect, so you can't reuse an earlier BFS, and each ask starts from scratch:

computers Vcables Easks QBFS work ≈ Q · (V + E)

What went wrong Every ask asks "is there a path?" all over again. But the answer only changes when a connect merges two groups, and groups only ever merge, never split. So keep the groups themselves, and an ask becomes "are a and b in the same group?"

"Group" here is L2's component: a set of vertices that can all reach each other. Groups work because, as algs4 puts it, "is connected to" is symmetric ("If p is connected to q, then q is connected to p"), transitive ("If p is connected to q and q is connected to r, then p is connected to r") and reflexive ("p is connected to p"). That's also why this lesson's tool doesn't apply to L6's one-way arrows: there, "a reaches b" says nothing about "b reaches a".

The fix: every group keeps a root

Each vertex stores one number, its parent: another vertex in the same group. Follow parents upward and you end at a vertex that is its own parent, the group's root. Two vertices are in the same group exactly when they reach the same root.

The first version, with no tricks:

parent: list[int] = list(range(n))   # start: everyone is their own root

def find(x: int) -> int:
    while parent[x] != x:            # climb until a vertex is its own parent
        x = parent[x]
    return x

def union(a: int, b: int) -> None:
    parent[find(a)] = find(b)        # a's ROOT now hangs under b's ROOT

def connected(a: int, b: int) -> bool:
    return find(a) == find(b)

union links the two roots. If it wrote parent[a] = b instead, a would leave its old group behind, and everything still hanging below a's old root would be cut off from a.

The failure: a chain

The same code, a different stream: connect 0 1, connect 0 2, connect 0 3, … (0 with every other vertex in turn).

Eventfind(0) followsparent after (n = 5)
connect 0 10 links[1, 1, 2, 3, 4]
connect 0 21 link (0→1)[1, 2, 2, 3, 4]
connect 0 32 links (0→1→2)[1, 2, 3, 3, 4]
connect 0 43 links[1, 2, 3, 4, 4]
0 → 1 → 2 → 3 → 4          one tree, and it's a chain

Each connect hung the whole group under a single new vertex, so the group got one level deeper every time. connect 0 k follows k − 1 links, which adds up to about n²/2. At n = 100 000 that's ≈ 5 000 000 000 steps, no better than BFS. CP-Algorithms names the failure: "the trees degenerate into long chains. In that case each call find_set(v) can take O(n) time" (Disjoint Set Union, verified 2026-11-05).

Fix 1: union by size

The chain grew because the big group kept going under the small one. Flip it: keep a size per root, and always hang the smaller tree under the bigger root, "we keep track of the size of each tree and always connect the smaller tree to the larger" (algs4 §1.5).

def union(a: int, b: int) -> None:
    ra, rb = find(a), find(b)
    if ra == rb:
        return                     # one group already; merging would double-count size
    if size[ra] < size[rb]:
        ra, rb = rb, ra            # make ra the bigger root
    parent[rb] = ra                # the smaller tree hangs under the bigger root
    size[ra] += size[rb]           # only the new root's size is updated

Same chain stream, now with this union:

naive:            0 → 1 → 2 → 3 → 4         find(0) follows 4 links
union by size:    1 → 0   2 → 0   3 → 0   4 → 0    every find follows at most 1

That stream happened to be friendly, but the guarantee holds for every stream: "The depth of any node in a forest built by weighted quick-union for n sites is at most lg n" (algs4 §1.5). The reason fits in one line. A vertex gets one level deeper only when its tree is hung under a tree at least as big, so the group it lives in at least doubles. A group of 1 can double only lg n times before it holds all n vertices. At n = 100 000, lg n ≈ 17.

Sizes live at roots The last line updates size at the new root only. Once a root gets a parent, its own size entry is never touched again, so it goes stale. That's why union compares size[ra] and size[rb], the roots, and never size[a] and size[b].

Fix 2: path compression

Every find climbs to the root and then forgets what it learned. The next find from the same vertex climbs the same links again. "Ideally, we would like every node to link directly to the root of its tree" (algs4 §1.5). So on the way back down, point every vertex you passed straight at the root:

def find(x: int) -> int:
    if parent[x] != x:
        parent[x] = find(parent[x])    # whatever root came back, x now points at it
    return parent[x]

That's CP-Algorithms' one-liner return parent[v] = find_set(parent[v]); written in Python. Trace it on the chain from the failure section, parent = [1, 2, 3, 4, 4]. Going up, find(0) calls find(1), which calls find(2), find(3), find(4). Vertex 4 is the root, so 4 comes back. Then each call writes it:

Returning fromWritesparent after
find(4)— (root)[1, 2, 3, 4, 4]
find(3)parent[3] = 4[1, 2, 3, 4, 4]
find(2)parent[2] = 4[1, 2, 4, 4, 4]
find(1)parent[1] = 4[1, 4, 4, 4, 4]
find(0)parent[0] = 4[4, 4, 4, 4, 4]

One find paid for 4 links. Every later find in that group pays 1.

Is the recursion safe? The recursion is as deep as the path, and union by size caps every path at lg n (≈ 17 at 100 000), far below Python's default limit of 1000. Without union by size, the chain stream recurses 100 000 deep and crashes, like L6's recursion test did. The two fixes protect each other.

All together

class UnionFind:
    def __init__(self, n: int) -> None:
        self.parent: list[int] = list(range(n))    # everyone is their own root
        self.size: list[int] = [1] * n             # trusted at roots only

    def find(self, x: int) -> int:
        if self.parent[x] != x:
            self.parent[x] = self.find(self.parent[x])   # path compression
        return self.parent[x]

    def union(self, a: int, b: int) -> None:
        ra, rb = self.find(a), self.find(b)
        if ra == rb:
            return
        if self.size[ra] < self.size[rb]:
            ra, rb = rb, ra                        # union by size
        self.parent[rb] = ra
        self.size[ra] += self.size[rb]

    def connected(self, a: int, b: int) -> bool:
        return self.find(a) == self.find(b)

Python's standard library has no union-find. You write these lines each time.

What it cost

One new word first. Amortized cost means the cost averaged over a long sequence of operations: one particular find can still be slow, but the total over m operations stays below m times the bound.

Versionone find (worst)m operations
BFS per ask (no union-find)O(V + E) per askO(m · (V + E))
parent links, naiveO(n), the chainO(m · n)
+ union by sizeO(log n)O(m log n)
+ path compressionamortized O(α(n))O(m · α(n)), effectively O(m)

α is the inverse Ackermann function, "which grows very slowly … it doesn't exceed 4 for all reasonable n (approximately n < 10600)" (CP-Algorithms). Treat it as a constant. Space: parent and size, O(n). No adjacency list is ever built, because each cable is used once, when it arrives, and then thrown away.

Check yourself

Why does a fresh BFS per ask get too slow?

BFS handles cycles fine (L2's visited set). The problem is repetition: the graph changes between asks, so each ask pays O(V + E) again from scratch.

union(a, b) has found ra and rb, with different sizes. Which link is written?

Roots are linked, never a and b themselves, and the smaller tree goes under. Hanging the bigger one under the smaller is what built the chain.

On the chain 0→1→2→3→4, right after a compressing find(0), what holds?

Every call on the way back writes the root into its own vertex, so the whole path gets compressed, not just the starting vertex.

Why compare size[ra] with size[rb], and not size[a] with size[b]?

union adds to the new root's size only. A vertex that was once a root keeps its old, stale size forever, and a vertex that never was one keeps 1.
