L2 — DFS on a Graph with Cycles: The Visited Set

Graphs track · lesson 2 of the main line · ~25 min + drill · 2026-08-18 · prereq: L1 — Graph Anatomy

The problem first — deliver a message, crash a program

Same five people as L1. A message starts at person 0 and spreads along friendships: everyone who hears it repeats it to all their friends. Who ends up hearing the message?

Two new names, both visible in the picture:

TermIn the picture
cyclea path that comes back to where it started without reusing an edge — the red triangle 0 → 1 → 2 → 0. Trees never have one; graphs may.
reachablev is reachable from u if some chain of edges leads from u to v. From 0: vertices 0, 1, 2, 3. Vertex 4 is not reachable from anywhere.

You already know a traversal that "spreads to all children": the DFS you wrote for trees and backtracking. Port it naively — recurse into every neighbor:

adj = {0: [1, 2], 1: [0, 2, 3], 2: [1, 0], 3: [1], 4: []}   # built in L1
heard: set[int] = set()

def dfs(u: int) -> None:
    heard.add(u)
    for v in adj[u]:
        dfs(v)          # a tree child never points back at its parent...

dfs(0)

Trace it on paper, one row per call — the L1 network, starting at 0:

#calladj[u]first thing it does
1dfs(0)[1, 2]recurse into 1
2dfs(1)[0, 2, 3]recurse into 0
3dfs(0)[1, 2]recurse into 1
4dfs(1)[0, 2, 3]recurse into 0
⋮⋮⋮…≈1000 frames later: RecursionError

On a tree this template was safe because no child ever points back — trees have no cycles, by definition. The undirected edge 0–1 alone already breaks that promise: 0 lists 1 as a neighbor and 1 lists 0 right back. The recursion tree you learned to draw in the D0 patch isn't just big here — it is infinite. No amount of cleverness in the recursion fixes a tree that never ends; you must stop re-entering vertices at all.

On the triangle 0–1–2–0, the tree-style DFS above (no protection), started at 0, does what?

Row 2 of the trace: 1's first neighbor is 0, which immediately recurses back into 1. The cycle 0–1–2 is never even needed — one undirected edge is already a two-vertex loop.

The fix: a visited set

Give the traversal a memory. visited is a set holding every vertex the DFS has ever entered; a vertex gets in once and never leaves. This is the single most important template of the whole track:

visited: set[int] = set()

def dfs(u: int) -> None:
    visited.add(u)              # mark FIRST — the moment u is reached
    for v in adj[u]:
        if v not in visited:    # enter each vertex at most once
            dfs(v)

dfs(0)

Trace it on the network, starting at 0 — full state table, your method:

#callvisited after markadj[u]decisions
1dfs(0){0}[1, 2]1 unseen → recurse (2 checked later, row 5)
2dfs(1){0, 1}[0, 2, 3]0 seen → skip; 2 unseen → recurse
3dfs(2){0, 1, 2}[1, 0]1 seen → skip; 0 seen → skip; return
4dfs(3){0, 1, 2, 3}[1](back in row 2: 3 unseen → recurse) 1 seen → skip; return
5—{0, 1, 2, 3}—back in row 1: 2 already seen → skip; done

Four calls, then silence. The answer to the opening problem: {0, 1, 2, 3} hear the message; 4 never does — exactly the set of vertices reachable from 0. The cycle did try to strike (rows 2 and 3, "0 seen → skip") and the set absorbed it.

Mark on entry, not on exit Move visited.add(u) to after the loop and the protection evaporates: in row 2, vertex 1 would look at neighbor 0 — still unmarked, since dfs(0) hasn't finished — and recurse straight back into it. Same infinite ping-pong, with a visited set sitting right there. The mark must land the moment the vertex is entered, before any neighbor is explored.

Marking u visited only AFTER its neighbor loop finishes, on the triangle 0–1–2–0, causes what?

A vertex only "counts as visited" once its whole subtree is done — but the cycle re-enters it long before that. Marks that arrive late are marks that don't protect.

This is NOT the backtracking undo — map the templates

The shape looks like your backtracking for-loop template, and that resemblance is a trap worth defusing head-on:

Your choose/explore/unchoose mechanics are correct and stay correct — for backtracking's question. Reachability asks a cheaper question, so it keeps its marks. Un-marking visited in a graph traversal doesn't make it "more thorough"; it makes it exponential or infinite.

The cost — count it, don't guess it

Two counts, then add (the recursion-tree discipline from D0):

  • Calls: dfs(u) only runs on an unmarked u and immediately marks it — so at most one call per vertex: V calls.
  • Loop iterations, summed over all calls: each call reads adj[u] once, so every list is read exactly once. The lists together hold every edge twice (u–v sits in adj[u] and in adj[v] — L1): 2E iterations.

Total: O(V + E). Added, not multiplied — no call re-reads another call's list. This number is the reason the whole track exists: the entire graph, cycles included, traversed in one linear pass.

DFS with a visited set over an adjacency list — V vertices, E edges — costs in total:

V for the calls plus 2E for the summed neighbor loops. Multiplying V by E would mean every call re-scans every edge — the visited set is precisely what forbids that.

Connected components: launch DFS until nobody is left

One launch of dfs(0) painted {0, 1, 2, 3} and stopped — it can only paint what is reachable. Vertex 4 (the isolated vertex L1 forced you to keep!) needs its own launch. Two more names, same picture:

TermIn the picture
connectedtwo vertices with some path between them: 0 and 3 are connected; 0 and 4 are not.
connected componentone whole "island" of mutually connected vertices. The network has two: {0, 1, 2, 3} and {4}.
launches = 0
for s in range(n):          # every vertex gets a chance to start
    if s not in visited:    # ...but only if no earlier launch painted it
        launches += 1
        dfs(s)              # paints exactly one component, then stops

The outer loop fires once per component — launches counts the components. The visited set is shared across launches: that is what stops component 1 from being counted four times (once per vertex).

Vertices 0–6, edges 0–1, 1–2, 3–4 and nothing else. How many times does the outer loop launch dfs?

Components: {0, 1, 2}, {3, 4}, {5}, {6}. Each launch paints one island; lone vertices are islands too — the L1 isolated-vertex trap, now with consequences.

Flood fill: the same DFS on the grid

Now port the template to the implicit graph from L1 — and settle a score from your drill review. On a grid, the traversal's neighbor condition splits into three separate questions, in this order:

R, C = len(grid), len(grid[0])
visited: set[tuple[int, int]] = set()

def flood(r: int, c: int) -> None:
    visited.add((r, c))                          # mark on entry, as always
    for dr, dc in ((-1, 0), (1, 0), (0, -1), (0, 1)):
        nr, nc = r + dr, c + dc
        if (0 <= nr < R and 0 <= nc < C          # 1. does the neighbor EXIST?   (anatomy — L1)
                and (nr, nc) not in visited      # 2. is it NEW?                 (this lesson)
                and grid[nr][nc] == grid[r][c]): # 3. am I ALLOWED to step there? (the problem's rule)
            flood(nr, nc)

Question 3 is where the cell's value finally gets used — as the label of a vertex, deciding where this particular problem lets the traversal walk ("stay on cells of the same value"). It is not an edge flag, and it is not part of anatomy: change the problem and question 3 changes with it, while questions 1 and 2 never move. One launch of flood paints one same-label region — this operation is called flood fill, the paint-bucket tool of every image editor, and it is the engine of your next two roadmap problems.

Same skeleton, three graphs Tree DFS, adjacency-list DFS, grid flood fill — one template. What varies is only how neighbors are produced (children / adj[u] / the four offsets) and what "allowed" means. Own the skeleton and every variation is a two-line edit.
