Reverse the Question

Graphs track · reference sheet · from L5 · see also BFS, DFS, Representations

The trigger

You reach for this the moment a problem asks:

"which vertices can reach T?"  (rather than "what can T reach?")

A traversal walks arrows forward from where it starts. A question about arrows pointing toward a target is pointing the wrong way. Answering it literally means one traversal per vertex: O((V+E)·V), or O((m·n)²) on a grid.

The rule

Inversion X reaches T in G  ≡  T reaches X in GT
A path is a list of vertices with an arrow at every consecutive pair. Reverse every arrow and the same list read backwards is still such a path. Nothing moved; the reading direction changed.

GT — the transpose or reverse graph — is "G with the edge directions reversed" (CP-Algorithms). One traversal from T over GT answers the question for every vertex at once: O(V+E).

Building GT on a grid: rewrite one line

You never materialise it. The direction lives in the neighbour test, so reversing the graph means rewriting that test from the point of view of the cell you are now standing on.

The one bug Reversing the search and leaving the condition alone. The code runs, terminates, and answers a different question. Sanity check every time: take one cell the reversed search claims, and walk it forwards to the target by hand.

Seeding a whole boundary

The target is usually a set (an edge, a border, every gate, every rotten orange), not one vertex. That is multiple-source reachability: "Given a digraph and a set of source vertices, is there a directed path from any vertex in the set to v?" (Sedgewick & Wayne §4.2).

sources = [ ... every boundary cell ... ]
seen  = set(sources)      # mark ALL seeds before the first pop
queue = deque(sources)
while queue:
    r, c = queue.popleft()
    for dr, dc in ((1,0), (-1,0), (0,1), (0,-1)):
        nr, nc = r + dr, c + dc
        if in_bounds(nr, nc) and (nr, nc) not in seen and REVERSED_CONDITION:
            seen.add((nr, nc))
            queue.append((nr, nc))
# `seen` is now every cell that reaches the boundary in the original direction

Costs one pass to collect the sources plus one traversal: Θ(m·n) either way — there is no cheaper case, the seeding scan alone reads every cell.

Second row's habit: when a rule has an escape hatch at the border, flood the border to find who escapes, then sweep everything you did not mark. Cheaper than testing each region for whether it touches an edge.

DFS or BFS?

Either. This is a reachability question, not a distance one — you want the set of reached cells, and both traversals reach the same set. Use BFS if you want the flat loop and no recursion-depth risk on a large grid; use DFS if the recursive form reads better. Layers are irrelevant here (contrast BFS as distance, where they are the whole point).
